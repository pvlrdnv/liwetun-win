# ADR-001 — independent Windows client

Status: initial development decision, 2026-11-15.

Implementation addendum: the official TrustTunnel deep-link parser is now
statically integrated through a bounded Rust/C ABI and Windows Flutter channel.
Windows compilation and actual channel tests passed on the disposable CI runner.
This supersedes the initial import-only availability limitation below; the
service boundary is now implemented with signature/ACL/SID/session checks.
Full SDK compilation, signed-service tests and bounded H2/H3/DNS TUN traffic
acceptance passed on disposable Server 2022 CI. Windows 10/11 installed-client
acceptance and ordinary global routing remain open. See WINDOWS_SERVICE.md and
TUN_NETWORK_ACCEPTANCE.md.
See NATIVE_IMPORT.md and STATUS.md for actual evidence and remaining gates.

## Context and scope

Owner authorized an independent repository in `liwetun-win`. Product: LiWeTun.
LikeWeb is undergoing concurrent work and must not be modified. The handoff
`likeweb-web/docs/LIWETUN_WINDOWS_HANDOFF_261115.md` was read as reference;
no production secrets or application code were copied into this repository.
LOCAL source inspection confirms the current general feed has VLESS/Hysteria2,
but no TrustTunnel. The client contract is a proposal, not a deployed API.

## Decision

- Flutter UI with a small domain layer independent of widgets.
- Windows acceptance targets: Windows 10 x64 and Windows 11 x64, per the owner
  clarification on 2026-11-15. Each desktop OS needs its own installed-client
  acceptance; ARM64 remains outside this stage. See WINDOWS_COMPATIBILITY.md.
- TrustTunnel first, using the official Windows SDK/service. Hysteria2 and
  VLESS/Xray follow after qualification. Xray TUN component is still undecided.
- One active tunnel; privilege boundary at authenticated local service IPC.
  UI runs as the user, installer installs service into administrator-writable
  Program Files. Do not expose a generic privileged command/config runner.
- Inspect SDK signer checks before integration. Preserve Wintun signatures.
  No shipped service with unsigned sibling-path fallback. No TLS bypass.
- All saved secrets use current-user Windows DPAPI with private ACLs and atomic
  compare-and-swap persistence. No plaintext fallback; see PROFILE_STORAGE.md.
- A prepared subscription snapshot is read separately from key provisioning.
  The client never calls panels, broker management or databases.
- The first slice kept native connection unavailable. The continuation adds
  authenticated Windows service control, with actual evidence in STATUS.md.
  Fail closed; no fake connected state or simulated success button.

## Dependencies and evidence

Flutter 3.38.10 tag: `c6f67dede3d4aa1aa7a69dd56a3494a5cde6cc80`.
This is a reproducible starting point, not a claim to be the latest release.
Dart/Flutter packages are recorded in pubspec.lock once resolved.
No TrustTunnel binaries are redistributed at this stage; SDK version, artifact
SHA256 and transitive license inventory must be pinned before integration.

Primary sources checked 2026-11-15:

- https://github.com/TrustTunnel/TrustTunnelClient/blob/master/platform/windows/README.md
- https://github.com/TrustTunnel/TrustTunnelClient/blob/master/trusttunnel/README.md
- https://docs.flutter.dev/platform-integration/windows/setup

SDK docs describe x86_64/aarch64 packages, Wintun, administrator requirements,
DLL start/stop, common embedded signing certificate for app and adapter/service
binaries. An installer signature alone is insufficient. Moving upstream docs
are research evidence, not a dependency lock or native test result.

## Deferred

Installer, signed updates/rollback, tray, subscription HTTPS fetch, bounded
retry/jitter, tunnel health and route-bound application probes, recovery, kill
switch and exceptions. Current Windows SDK/service/authentication, icon and
protected storage implementations are documented in STATUS.md; desktop and
release acceptance remain separate gates.
